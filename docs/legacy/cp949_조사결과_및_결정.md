# .bat 배치 파일 CP949/한글 깨짐 버그 조사 결과 (2026-07-13)

## 배경
NAS 배포 방식을 robocopy에서 git pull 기반으로 전환하면서, 팀원용 실행
bat들이 python을 호출하기 전에 공통으로 거치는 내부 헬퍼
(`_최신코드자동확인.bat` → 이번 조사 후 `_auto_git_pull.bat`로 개명)를
추가했다. 이 헬퍼에 `chcp 65001`(UTF-8 코드페이지)과 한글 주석/메시지를
넣었는데, 한국어 Windows 콘솔(기본 코드페이지 CP949)에서 배치 파일이
깨지는 문제가 발견되어 원인을 조사했다.

## 1. CP949 버그의 정확한 원인

cmd.exe는 배치 파일에 인코딩 메타데이터가 없으므로, 파일을 읽을 때
**그 순간 콘솔에 활성화된 코드페이지**로 바이트를 해석한다. 파일이
UTF-8로 저장되어 있어도, 실행 시점의 콘솔이 한국어 Windows 기본값인
CP949 상태라면 UTF-8 멀티바이트 시퀀스가 CP949 기준으로 잘못
디코딩된다. 이 오디코딩된 결과가 하필 공백/따옴표/괄호 같은 구문상
의미 있는 문자와 겹치면, cmd의 토크나이저가 원래 한 줄(`rem` 주석,
`echo` 문자열)을 여러 개의 서로 다른 "명령어"로 잘못 쪼개서 실행을
시도한다.

파일 맨 위에 `chcp 65001`을 넣어도 이 문제를 근본적으로 막지 못한다.
`chcp 65001` 줄 자체는 ASCII라 문제없이 실행되지만, cmd.exe의 배치
파서는 `if (...)`/`for (...)`처럼 괄호로 묶인 복합 블록을 파싱 시점의
코드페이지로 한 번에 룩어헤드(lookahead) 읽어들이기 때문에, 그 안에
있는 한글 텍스트는 여전히 전환 이전 코드페이지 기준으로 잘못 해석될
여지가 있다. 즉 "UTF-8 저장 + chcp 65001"은 한글이 단순 `echo` 한 줄에만
있어도 안전을 보장하지 못하는, 근본적으로 불안정한 조합이다.

## 2. 최종 결정 — 파일명 + 인코딩 통일 방침

**결론: 모든 .bat 파일 "본문"은 순수 ASCII(영문)로 통일한다. `chcp`
지정은 전부 제거한다. 파일명도 ASCII로 바꿀 수 있는 경우(내부 전용
헬퍼)는 ASCII로 개명한다.**

**(추가 결정, 같은 날 후속 논의)** 팀원에게 보여줄 알림 메시지는
한글로 유지하기로 했다. 단, `.bat` 파일 본문에 한글 바이트를 직접
넣지 않고, PowerShell `-EncodedCommand`(메시지를 UTF-16LE로 인코딩한
뒤 Base64로 감싼 것)를 통해 출력하는 방식을 쓴다. 예:

```
powershell -NoProfile -EncodedCommand VwByAGkAdABlAC0ASABvAHMAdAAgACcAWwBMxby5XQAgAFzN4MIgAFTP3LQgAFXWeMcgAOTCKNMsACAAMK50yCAAVM/ctFy4IADEyYnVadXIsuSyLgAnAA==
```

이 Base64 문자열은 A-Z/0-9/+/=만 쓰는 순수 ASCII이므로 `.bat` 파일
본문은 여전히 100% ASCII를 유지하면서(1번에서 설명한 cmd.exe 코드페이지
버그의 영향권 밖), 한글 디코딩·출력은 cmd.exe의 배치 파서를 거치지
않는 PowerShell 프로세스가 전담한다. `_auto_git_pull.bat`의 "pull 실패
시 알림" 메시지가 이 패턴의 실제 적용 예시다.

- **CP949 재저장**이 아니라 **ASCII**를 택한 이유: CP949로 저장하면
  "실행 대상 PC의 콘솔이 항상 CP949"라는 가정에 계속 의존하게 되고,
  이 가정이 어긋나는 환경(Windows Terminal의 UTF-8 기본 설정, 로케일이
  다른 PC 등)에서는 동일한 문제가 재발할 수 있다. ASCII는 콘솔의
  코드페이지가 무엇이든(CP949, UTF-8, OEM 437 등) 바이트 해석이
  달라지지 않으므로 원천적으로 이 버그 클래스 자체가 발생하지 않는다.
- **UTF-8 BOM 유지 + chcp 65001 유지**도 채택하지 않았다. BOM은 cmd.exe
  배치 파서가 인식하지 못해 첫 줄(`@echo off`) 앞에 깨진 문자가 붙는
  별도 문제를 일으키고, 근본 원인인 "괄호 블록 룩어헤드 시 코드페이지
  불일치"는 여전히 해결되지 않는다.
- **파일명 개명**: `_최신코드자동확인.bat`은 오늘 새로 추가된
  내부 전용 헬퍼(팀원이 직접 더블클릭하지 않고, 다른 bat들이 `call`로만
  호출)이고 문서/NAS 등 외부에 아직 알려지지 않은 파일이라 부담 없이
  개명 가능했다. `_auto_git_pull.bat`으로 바꿔서, 이 파일을 `call`하는
  4개 실행 bat의 호출 구문에서도 한글 파일명 바이트가 아예 사라지게
  했다. 반면 `실행.bat`/`DB업데이트만.bat`/`보고서만생성.bat`/
  `전년대비보고서만생성.bat`처럼 팀원에게 이미 익숙하고 NAS 바탕화면
  아이콘·문서에 쓰이는 한글 파일명은 이번 조사 범위에서 개명하지
  않았다(별도 결정 필요 사항).

## 3. 파일별 최종 인코딩 확인 (`file` 명령 결과)

| 파일 | `file` 명령 결과 | 비고 |
|---|---|---|
| `_auto_git_pull.bat` | DOS batch file, ASCII text | 신규 개명, `chcp` 제거, 한글 알림 메시지는 `-EncodedCommand`로 출력 |
| `실행.bat` | DOS batch file, ASCII text, with CRLF line terminators | `call` 대상만 `_auto_git_pull.bat`로 수정 |
| `DB업데이트만.bat` | DOS batch file, ASCII text | `chcp 65001` 줄 삭제, `call` 대상 수정 |
| `보고서만생성.bat` | DOS batch file, ASCII text, with CRLF line terminators | `call` 대상만 수정 |
| `전년대비보고서만생성.bat` | DOS batch file, ASCII text, with CRLF line terminators | `call` 대상만 수정 |

5개 파일 모두 `file` 결과가 "ASCII text"로 확인되어(UTF-8 표기 없음),
non-ASCII 바이트가 전혀 남아있지 않은 상태다. 참고로 파일 자체의
한글 이름(`실행.bat` 등)은 NTFS가 유니코드로 별도 관리하는 파일
시스템 메타데이터라 이 인코딩 문제와 무관하며, 배치 파일 "본문"에
non-ASCII 바이트가 없는지가 관건이다.

## 4. 기존 `DB업데이트만.bat`의 `chcp` — 왜 지웠나

`DB업데이트만.bat`은 V8 최초 커밋(824a3e3) 때부터 `chcp 65001 > nul`을
가지고 있었지만, 그 시점 본문은 영문 echo 메시지("DB update only V8
Final Release" 등)뿐이라 실제로는 non-ASCII 바이트가 하나도 없었다.
그래서 `file` 결과도 계속 "ASCII text"였고, `chcp 65001`이 있어도
디코딩할 멀티바이트 문자가 없으니 지금까지 문제없이 동작해온 것이다
(버그가 "잠재"해 있었을 뿐 "발현"하지 않았던 상태).

오늘 이 파일에 `call "%~dp0_최신코드자동확인.bat"` 줄이 추가되면서
처음으로 한글 바이트(파일명)가 본문에 들어왔고, 이 상태로 남겨두면
1번에서 설명한 CP949/UTF-8 코드페이지 불일치 버그가 실제로 발현될
조건이 갖춰진다. 따라서:

1. `call` 대상을 ASCII 파일명 `_auto_git_pull.bat`으로 바꿔 한글
   바이트 자체를 제거했고,
2. 더 이상 대응해야 할 non-ASCII 콘텐츠가 없으므로 무의미해진
   `chcp 65001 > nul` 줄도 함께 삭제했다.

결과적으로 `DB업데이트만.bat`은 최초 커밋 때와 마찬가지로 순수
ASCII 상태(`file` 결과: "DOS batch file, ASCII text")로 되돌아갔다.

## 5. ⚠️ 미해결 — 실제 더블클릭 환경에서의 최종 검증은 아직 안 됨

지금까지의 "EncodedCommand로 한글이 정상 출력된다"는 결론은 **추론이며,
실제 더블클릭 환경에서 확정된 것이 아니다.** 검증한 방식은:

1. `_auto_git_pull.bat`과 동일한 실패 분기를 가진 테스트용 사본
   (`test_forced_fail.bat`)을 이 PC의 로컬 sandbox(`$env:TEMP\battest`)에서
   강제로 git pull이 실패하도록 만들어 실행했다.
2. 출력을 콘솔이 아니라 **파일로 리다이렉트**했고, 그 결과 PowerShell이
   Write-Host 결과를 CLIXML로 감싸서 내보냈다(리다이렉트 시 발생하는
   정상적인 부가 동작).
3. 그 CLIXML 안의 `Message` 필드 바이트를 CP949로 수동 디코딩했더니
   원래 의도한 문자열 "[알림] 최신 코드 확인 실패, 기존 코드로
   진행합니다."과 정확히 일치했다.

즉 **바이트 수준으로는** 올바른 한글 텍스트가 만들어진다는 것까지만
확인했고, **실제 한국어 Windows 콘솔 창에 직접 출력했을 때 화면에
깨지지 않고 보이는지는 눈으로 확인하지 않았다.** 리다이렉트 여부에
따라 PowerShell의 출력 경로(콘솔 호스트 직접 출력 vs CLIXML 직렬화)가
달라지므로, 이번 검증 방법이 실제 더블클릭 시나리오(리다이렉트 없음)의
동작을 100% 보장하지는 않는다.

**따라서 `feature/nas-git-deploy`를 main에 병합한 뒤, 반드시 실제
한국어 Windows PC에서 `실행.bat`(또는 pull이 실패하는 조건을 인위적으로
만든 뒤 `DB업데이트만.bat` 등)을 더블클릭해서, 콘솔 창에 한글 알림
메시지가 깨지지 않고 정상 출력되는지 눈으로 확인해야 한다.** 이
검증이 끝나기 전까지는 이번 결정이 "실전 검증 완료"가 아니라
"로컬 sandbox 기반 추론"임을 유의할 것. (동일 항목이 `CLAUDE.md`의
".bat 파일 작성 규칙" 절에도 할 일로 등록되어 있다.)

## 6. 실기기 검증에서 실제로 발견된 문제 — dubious ownership (CVE-2022-24765)

병합 후 실제 팀원 PC에서 NAS의 `실행.bat`을 더블클릭했을 때 "[알림]
최신 코드 확인 실패, 기존 코드로 진행합니다."가 떴다. 5번 항목에서
우려한 "한글이 콘솔에서 깨지는" 문제는 아니었고(메시지 자체는 정상
출력됨), **`_auto_git_pull.bat` 내부의 `git pull`이 조용히 실패하고
있었다.**

`_auto_git_pull.bat`은 `git ... pull >nul 2>&1`로 stderr를 항상
버리기 때문에 진짜 원인이 화면에 안 보였다. 원인을 밝히려고 NAS UNC
경로에서 `git -C "...\salary_system_claude" pull --ff-only`를 직접
(에러 숨김 없이) 실행해 재현했고, 정확히 아래 에러였다:

```
fatal: detected dubious ownership in repository at '//nas/CN_AMD/판매수수료 관련자료/salary_system_claude'
'//nas/CN_AMD/판매수수료 관련자료/salary_system_claude' is owned by:
	(inconvertible) (S-1-5-21-248651995-3952852001-1963251382-3056)
but the current user is:
	DESKTOP-7MD7NVM/azmang (S-1-5-21-1462429410-146580474-929953457-1001)
To add an exception for this directory, call:

	git config --global --add safe.directory '%(prefix)///nas/CN_AMD/판매수수료 관련자료/salary_system_claude'
```

**원인**: Git 2.35.2부터(CVE-2022-24765 대응) 저장소 소유자 SID와
현재 로그인 사용자 SID가 다르면 git이 해당 저장소에서의 명령을
전부 거부한다. NAS(SMB 공유)는 SMB 레이어가 보고하는 소유자 SID가
로컬 로그인 계정과 구조적으로 일치하지 않는 경우가 흔하고(이번엔
아예 `(inconvertible)` — SID 자체를 변환하지 못함), 이 때문에 git
저장소가 네트워크 경로에 있으면 이 검사에 걸리기 매우 쉽다. 이
PC(azmang 개발 PC)는 예전부터 전역 설정에 `safe.directory = *`
(모든 저장소 신뢰)가 걸려 있어서 지금까지 이 문제를 겪지 않았을
뿐이고, 이 설정이 없는 팀원 PC들은 첫 실행부터 걸릴 수밖에 없었다.

### 왜 인라인 Base64(`-EncodedCommand`)가 아니라 별도 `.ps1` 파일로 분리했나

이 self-heal 로직(설정 확인 → 필요 시 추가 → pull 재시도 → 그래도
실패하면 한글 알림)을 처음에는 4번/5번 항목과 같은 방식으로
`-EncodedCommand`(Base64) 한 줄로 `.bat` 안에 박아 넣으려 했다.
그런데 로직이 여러 줄(git config 조회, 조건문, 재시도, 조건부 알림)로
늘어나면서 "코드가 눈에 안 보이고 Base64 문자열 뭉치만 남는" 문제가
생겼다 — 나중에 사람이 이 로직을 감사(audit)하거나 디버깅하려면
Base64를 다시 디코딩해야만 내용을 볼 수 있어 실용성이 떨어진다.

그래서 이 로직 전체를 `_pull_retry.ps1`(사람이 읽을 수 있는 일반
텍스트, UTF-8 with BOM)로 분리하고, `_auto_git_pull.bat`은
`powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0_pull_retry.ps1"`
한 줄로 그 파일을 호출만 하도록 바꿨다. `.ps1` 파일 자체는 cmd.exe의
배치 파서를 거치지 않고 PowerShell이 직접 읽으므로(BOM으로 인코딩을
명시), 1번에서 설명한 cmd.exe 코드페이지 버그의 영향권 밖이면서도
Base64로 감추지 않은 평문 코드로 유지된다. `.bat` 본문은 여전히
100% ASCII를 유지한다.

### 발견된 버그: PowerShell `-notcontains`의 유니코드 문자열 비교 실패

`_pull_retry.ps1` 최초 버전은 이미 등록된 값인지 아래처럼 확인했다:

```powershell
$existing = git config --global --get-all safe.directory 2>$null
if ($existing -notcontains $safeDirValue) {
    git config --global --add safe.directory $safeDirValue
}
```

로컬 sandbox에서 같은 스크립트를 두 번 실행했더니(1차: 미등록 →
추가, 2차: 이미 등록됨 → 추가하면 안 됨), **2차 실행에서도 다시
추가되어 `safe.directory`에 완전히 동일해 보이는 문자열이 두 줄
중복 등록되는 버그를 발견했다.** 화면에 찍힌 두 줄은 육안상 완전히
같은 문자열이었는데도 PowerShell의 `-notcontains`가 "다르다"고
판단한 것 — `git config --get-all`로 되돌아온 문자열과 스크립트
안의 리터럴 문자열이, 표시상으로는 같아 보여도 유니코드 정규화
형태(NFC/NFD 등) 차이나 캡처 과정의 미세한 인코딩 차이로 인해 완전
동일한 바이트열이 아니었을 가능성이 높다(정확한 바이트 차이까지는
추적하지 않음).

**수정**: PowerShell 쪽에서 문자열을 직접 비교하는 대신, git 자신에게
"이 값이 이미 등록돼 있는지" 물어보는 방식으로 바꿨다:

```powershell
git config --global --fixed-value --get-all safe.directory $safeDirValue *> $null
if ($LASTEXITCODE -ne 0) {
    git config --global --add safe.directory $safeDirValue
}
```

`--fixed-value`는 git config가 값 패턴을 정규식이 아니라 리터럴
문자열로 비교하게 하는 옵션이다. 이렇게 하면 문자열 비교를 git 자신의
config 파서(내부적으로 항상 저장된 바이트와 정확히 비교)에 맡기게
되어, PowerShell 레이어에서 발생할 수 있는 인코딩/정규화 불일치
문제를 원천적으로 피한다.

### 실제 NAS 환경에서 재검증 완료

수정 후 실제 NAS UNC 경로(`\\nas\CN_AMD\판매수수료 관련자료\salary_system_claude`)에
`_auto_git_pull.bat`/`_pull_retry.ps1` 테스트 사본을 배포하고, 이
PC의 전역 `safe.directory = *`를 일시적으로 해제해 실제 팀원 PC와
동일한 "미등록" 상태를 재현한 뒤 검증했다:

1. **1차 실행** (`safe.directory` 미등록 상태): 첫 `git pull`이
   dubious ownership으로 실패 → `_pull_retry.ps1`이 미등록임을
   확인하고 정확히 이 NAS 경로 하나만(`*` 아님) 추가 → pull 재시도
   성공 → 종료 코드 0, 한글 알림 없음. 이후 `git config --global
   --get-all safe.directory` 결과 이 NAS 경로 한 줄만 등록됨을 확인.
   NAS git HEAD도 최신 커밋(`b580db8`, PR #37 포함)까지 정상 반영됨.
2. **2차 실행** (`safe.directory` 이미 등록된 상태에서 `_pull_retry.ps1`만
   재호출): `--fixed-value` 조회가 이미 등록된 값을 정확히 찾아내
   추가를 건너뜀 → pull 재시도(이미 최신이라 "Already up to date")
   → 종료 코드 0. `git config --global --get-all safe.directory`
   등록 줄 수가 여전히 1개로 유지됨(중복 없음) 확인.

테스트 완료 후 NAS의 테스트 사본은 정리했고(추적 파일은 `git checkout --`로
원복, 미추적 테스트 파일은 삭제), 이 PC의 전역 설정도 원래대로
`safe.directory = *`로 복구했다.

이 항목은 5번 항목과 별개다 — 5번은 "한글 메시지가 콘솔에 깨지지
않고 나오는지"에 대한 미검증 항목이고(여전히 실제 눈으로 확인 안
됨), 6번은 그와 별개로 실기기에서 실제로 터진 "pull 자체가 실패하는"
근본 원인과 그 수정을 다룬다.
